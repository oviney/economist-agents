# Harness engineering assessment — `economist-agents` vs SE Radio 730

**Date:** 2026-07-29
**Reviewer:** Claude (Opus 5), at the owner's request
**Source under review:** `SE Radio 730: Birgitta Boeckeler on Harness Engineering for AI Agents`
(released 2026-07-22; transcript at `~/code/podcast-scriber/`)
**Subject under review:** the Claude Code harness layer of this repo — `CLAUDE.md`,
`skills/`, `.claude/`, `.mcp.json`, `.pre-commit-config.yaml`, `make ci-local`
**Verdict:** guide-maximal, sensor-disconnected. Remediation specced in
`docs/specs/harness-engineering.md`; scheduled as **B-030 … B-034**.

---

## 1. The framework being applied

Boeckeler's argument is cybernetic: a codebase is a system you are *regulating*, and you
have exactly two instruments.

| Instrument | Direction | Manifests as |
|---|---|---|
| **Guides** | Feed-forward — anticipate what you want and don't want | Markdown (`CLAUDE.md`, `AGENTS.md`, skills). *Normative* (conventions) or *informative* (architecture, context). Can also be **computational** — codemods, OpenRewrite. |
| **Sensors** | Feedback — let the agent detect its own error and self-correct *before a human looks* | **Inferential** (a review skill, another model) or **computational** (static analysis, tests, coverage, security scans). |

Three claims from the episode drive this assessment:

1. **Guides are the weakest instrument, and volume makes them weaker.**
   > "I just don't see the future as being like 50 markdown files in our code base… and
   > then in every markdown file we have very, very important, do the following, never do
   > the following. I mean, that can't be it. Can we still call ourselves engineers if
   > that's how we're doing stuff?"

2. **A sensor only counts if the *agent* closes the loop, not the human.**
   > "Then the analysis tool says, over there, cyclomatic complexity is too high… And then
   > that starts another little loop where the agent tries to self-correct and then asks
   > the sensor again."

3. **An always-green sensor is a liability, not an asset.**
   > "If my pipeline is always green, is that a good thing? It's actually not, right? You
   > want it to go red sometimes. Because that gives you the good feeling that, oh yeah,
   > it's actually a safety net that works. If it's always green, I would get suspicious."

Two secondary claims matter for scheduling: **guides should be eval'd** (run a scenario
with and without the skill; delete the skill if the score doesn't move — especially since
"many skills these days are actually generated by large language models", so the model may
already know their content), and **sensor state should be observable over a session**
("how did the test coverage evolve? How did the number of analysis violations evolve?").

## 2. Scorecard

| Dimension | Grade | Evidence |
|---|---|---|
| Guides — content quality | **A−** | `CLAUDE.md` is genuinely strong: stack, commands, boundaries, an ADR-linked constraint block, an explicit skill-routing contract. |
| Guides — volume / discipline | **D** | 8,031 lines across 38 `SKILL.md` + 210-line `CLAUDE.md` + **2,601-line** `.github/copilot-instructions.md` + `GEMINI.md` + root `copilot-instructions.md`. |
| Sensors — computational inventory | **B+** | ruff, mypy, pytest + coverage (70% / `src/quality` 90%), bandit, `destructive_change_guard`, `pre_commit_arch_check`, `lint_adrs`, `validate_skills`, `check_bare_name_imports`, `publication_validator`, `citation_verifier`, `article_evaluator`. |
| Sensors — wired into the agent loop | **F** | **Zero hooks.** No project `.claude/settings.json` exists; `.claude/settings.local.json` holds 122 permission entries and no `hooks` key. User-level hooks are two `terminal-notifier` calls. |
| Sensor honesty | **D** | Four sensors that structurally cannot fail (§3.3). |
| Maintainability regulation | **F** | No complexity sensor of any kind (§3.2). |
| Effectiveness measurement | **F** | Product evals exist (`logs/article_evals.json`); **harness** evals do not. Nothing measures whether any of the 38 skills changes an outcome. |
| Observability / traces | **D** | `scripts/agent_trace_logger.py` is complete, schema-versioned and secret-redacting — and its only importer is its own test. |

**One-line verdict.** The repo has an excellent guide layer and an excellent sensor
*inventory*, and never connected them into a loop. Every sensor fires at the human's gate.
The human is the loop.

## 3. Findings

### 3.1 The sensors fire after the agent has left the room

Every computational sensor in the repo is bound to `pre-commit`, `pre-push`, or
`make ci-local` — the *owner's* gate. A Python edit made by an agent produces no signal
until the owner types `make ci-local`, at which point the agent's session context is stale
and the owner does the triage.

This is the inverse of the episode's model, in which the agent queries a sensor sidecar
mid-session and re-queries after fixing. The mechanism that would close that loop —
**hooks** — is the one harness feature the repo does not use at all.

Highest-leverage finding in this document. It is configuration plus a few small scripts,
not architecture.

### 3.2 No maintainability sensor — the exact failure mode the episode names twice

`ruff.toml` selects `E, W, F, I, UP, B, C4, SIM`. It contains no `C901`, no `PLR`, no
`max-complexity` (grepped: zero hits). Measured on `src/` + `scripts/` during this review:

```
41  C901     complex-structure          worst: generate_economist_post (33 > 10)
                                        validate (28), review_writer_output (24),
                                        apply_editorial_fixes (21), run_editorial_board (20)
28  PLR0912  too-many-branches
21  PLR0913  too-many-arguments
18  PLR0915  too-many-statements
 8  PLR0911  too-many-return-statements
```

Boeckeler names over-long functions and cyclomatic complexity as *the* characteristic
failure modes of AI-written code, "even with the big models." In a repo where an agent
writes most of the code, this dimension is entirely unregulated.

Her adoption technique is the right one for a 41-violation legacy baseline: **override the
lint message** so it does not merely report a number but instructs a judgment call —
refactor, or raise the threshold *for this function* with a recorded justification the
owner can review later. That reaches a clean baseline without a wall of violations, and
the recorded overrides become the review queue.

### 3.3 Four sensors that cannot fail

| Sensor | Why it is inert |
|---|---|
| **mypy** | `stages: [manual]` in `.pre-commit-config.yaml`; `strict = False`, `check_untyped_defs = False` in `mypy.ini`; and `make ci-local` wraps it in `\|\| echo "⚠️ mypy advisory — known debt, non-blocking"`. `CLAUDE.md` states **"Type hints mandatory."** The guide asserts; the sensor abstains. |
| **coverage (pre-push)** | `stages: [manual]` → never runs on push. Two thresholds coexist: `make test` uses `--cov-fail-under=40`, `make ci-local` uses `70`. |
| **badge validation** | `entry: bash -c 'python3 scripts/validate_badges.py \|\| true'`. Cannot fail by construction. Its stated purpose is preventing BUG-023 — stale badges. |
| **`validate-skills`** | Registered **twice** with the same hook `id`, and the second copy has `always_run: false` duplicated as a YAML key. |

The canonical instance is already in the backlog. **B-029**:
`scripts/acceptance_blog_frontmatter.sh:120` constructs
`STAGED="$BLOG/_posts/2026-01-01-${SLUG}.md"` instead of consuming the filename
`deploy_to_blog` actually produced. The documented oracle passed with 0 errors while the
deploy path emitted an unpublishable filename. *An oracle that renames its input is not
testing the deploy path.* That is the always-green warning, realised in production.

### 3.4 Where a guide and a default disagree, the default wins

**B-028**: the B-013 review stage exists as prose in a completed-backlog entry, while
`scripts/deploy_to_blog.py:681` sets `default="post"`. Running the documented command
silently produces an unreviewed publish — no error, no warning.

This is the episode's thesis reproduced exactly: the policy was written as a *guide*, so it
was skippable. Expressed as a *sensor* — a `PreToolUse` deny on `deploy_to_blog` invoked
without `--mode review` — it becomes unskippable.

The same asymmetry applies to the strongest guide in the repo. `CLAUDE.md` constraint #1,
**"NO new API keys. Ever."**, is the most emphatic sentence in the codebase and has zero
computational backing: neither `destructive_change_guard.py` nor `pre_commit_arch_check.py`
mentions `OPENAI_API_KEY` or `SERPER_API_KEY`.

### 3.5 The harness offers the agent tools its own guides forbid

`.mcp.json` still ships two servers whose declared `env` requirements are prohibited:

| Server | Requires | Forbidden by |
|---|---|---|
| `image-generator` | `OPENAI_API_KEY` | constraints #1, #2, #4; ADR-0014 retired the DALL-E path |
| `web-researcher` | `SERPER_API_KEY` | constraints #1, #2, #3; removed by #438 |

And `.claude/settings.local.json` sets `enableAllProjectMcpServers: true`, so both load
every session. The tool description presented to the agent reads *"Generates
Economist-style editorial illustrations using DALL-E 3. Requires the OPENAI_API_KEY
environment variable"* — in direct contradiction of the guide it is sitting next to.

> "It also cannot be just like throwing 100 tools at the agent and like 50 sensors that
> kind of overload it."

Deleting two entries removes the contradiction, shrinks the tool surface, and retires prose
whose only job is to say "don't use the thing that is right there."

### 3.6 Observability was built, then abandoned

`scripts/agent_trace_logger.py` implements exactly what the episode calls for — structured
per-stage traces, `TRACE_SCHEMA_VERSION`, automatic redaction of a `_SENSITIVE_KEYS`
frozenset — and `skills/agent-traceability/SKILL.md` documents it. Grepped across `src/`,
`scripts/`, and `tests/`: **the only importer is `tests/test_agent_trace_logger.py`**. It is
dead code.

Nothing records sensor state over the course of a session, so the question "did violations
spike mid-session and then resolve?" cannot be asked. The constituent parts exist
(`agent_metrics.py`, `chart_metrics.py`, `quality_dashboard.py`); the session-keyed
time series does not.

## 4. Recommendations, in leverage order

| # | Item | Recommendation | Why it ranks here |
|---|---|---|---|
| A | **B-030** | Commit a project `.claude/settings.json` with `PostToolUse` / `PreToolUse` / `Stop` / `SessionStart` hooks; record a sensor snapshot per session to `logs/sensor_history.jsonl` via the revived trace logger. | Converts the entire existing sensor inventory from human-gated to agent-gated. Configuration, not architecture. |
| B | **B-031** | Make the four inert sensors honest: un-manual mypy (or drop "mandatory" — the sensor becomes the source of truth), one coverage threshold, delete `\|\| true`, dedupe `validate-skills`. | An always-green gate manufactures confidence. Cheapest real risk reduction available. |
| C | **B-032** | Enable `C901` + `PLR09xx` with `max-complexity = 10`, delivered through a wrapper that emits the judgment-call message and a recorded per-function override path. | Regulates the dimension AI code reliably violates; the override mechanism is what makes 41 pre-existing violations tractable. |
| D | **B-033** | Build a with/without skill-eval harness; measure the five highest-traffic skills; merge or delete anything that does not move a score. | 8,031 lines of guide have never been measured. `.github/copilot-instructions.md` (2,601 lines) is the likeliest pure dead weight. |
| E | **B-034** | Delete the `image-generator` and `web-researcher` MCP entries; replace `enableAllProjectMcpServers: true` with an explicit list. | Removes a live guide/tool contradiction. Smallest diff in the set. |

**Sequencing note.** E → B → C → A → D is the correct *implementation* order even though
A is the highest-leverage: E and B are near-zero-risk cleanups, C supplies a sensor for A
to wire, A wires everything, and D depends on A's session recording to be worth running.

**One caution the episode would raise about A.** Hooks that fire on every edit can become
the noise overload that made everyone stop watching the Sonar server in the corner. Start
with the formatter/complexity `PostToolUse` pair and the `Stop` gate; add the rest only
once they have earned their place.

## 5. What this repo already gets right

Worth stating plainly, because the grades above are unflattering and the underlying
engineering is not.

- **`CLAUDE.md` is a genuinely good normative guide** — commands, boundaries, an
  ADR-linked non-negotiable constraint block, and an explicit skill-routing contract with a
  missing-skill rule. Most repos have nothing comparable.
- **The sensor inventory is broad and real** — architecture-compliance tests, a destructive
  change guard, an ADR linter, a skill-anatomy validator, a bare-name-import checker.
  These are second-order sensors most teams never build.
- **The regulated dimensions are correctly identified.** `ci-local` regulates correctness,
  security, and coverage; `publication_validator` and `article-evaluation` regulate product
  quality; ADR-0016 was drafted the same day precisely because a deterministic sensor was
  found unable to distinguish "cited" from "cited correctly" — which is the episode's
  inferential-vs-computational distinction, discovered independently.
- **B-028 and B-029 are this episode's two central warnings, self-diagnosed.** A guide the
  default ignores, and an oracle that cannot fail. The diagnosis was already right; what
  was missing was the framework that says these are the *same* defect.

The gap is not judgement. It is wiring.
